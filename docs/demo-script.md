# 5 分钟演示脚本

## 0. 演示前检查

```bash
# 1) 安装依赖（首次）
python -m venv .venv
.venv/Scripts/pip install -r requirements-dev.txt    # Windows
# source .venv/bin/activate && pip install -r requirements-dev.txt   # macOS/Linux

# 2) 清理旧数据，重新导入演示知识库
rm -rf data
python scripts/seed.py

# 3) 可选：验证真实模型
python scripts/smoke.py

# 4) 启动
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

打开 <http://127.0.0.1:8000>。

- 没有 `.env`：默认 `LLM_PROVIDER=mock`，页面徽标显示“离线演示”，全部流程可跑。
- 有 DeepSeek Key：`cp .env.example .env`，填 `LLM_API_KEY`，将 `LLM_PROVIDER` 设为 `deepseek`，重启。
- 演示时先说明当前模式，避免把 Mock 回答当成真实模型效果。

## 1. 政策问答（约 40 秒）

输入或点击建议：

> 七天无理由退货有什么条件？

预期：

- 助手给出 7 天、未安装/不影响二次销售、滤芯等例外；
- 正文有 `[S1]` 等引用；
- 展开“参考来源”，看到文档标题、章节、片段；
- 展开“工具调用”，看到 `search_knowledge_base`、耗时和结果摘要。

讲解点：知识库检索 → 提示词约束引用 → 前端只渲染真实来源。

## 2. 订单 + 政策组合（约 60 秒）

> 订单 A2026001 物流三天没更新，能退货吗？

预期：

- 工具轨迹先 `lookup_order`，再 `search_knowledge_base`；
- 回答同时包含订单状态（已发货、净水器 X3、物流停滞）和物流/退货政策；
- 引用来自知识库，订单信息来自工具，不编造。

讲解点：Agent 自主决定调用顺序；工具结果是事实，知识库是政策依据。

## 3. 建工单与幂等（约 60 秒）

> 订单 A2026001 物流异常，帮我建工单。

预期：

- 工具轨迹出现 `create_ticket`；
- 回答给出工单号 `T...`；
- 再发一次同样的话：工具轨迹显示“重复请求，返回已有工单”，工单数不增加。

查看统计：左下角 / 或 `GET /api/stats`，`tickets` 保持 1。

讲解点：会话内订单校验 + 幂等键 + 第三方 API 重试；不重复打扰客户系统。

## 4. 越权查询（约 30 秒）

> 查一下订单 A2026011 现在到哪了？

预期：拒绝，提示“未找到该订单，或该订单不属于当前账户”。

讲解点：订单表带 `customer_id`；查不到与无权统一措辞，避免订单号枚举。

## 5. 文档上传与增量检索（约 60 秒）

1. 点击知识库右上角「＋」。
2. 上传一段新的售后说明，例如“以旧换新补贴 300 元，回收后 3 个工作日发券”。
3. 等待“文档已入库”。
4. 提问：

> 以旧换新补贴怎么申请？补贴多少钱？

预期：回答引用新文档；来源里出现刚上传的文件名。

讲解点：上传 → 解析/切分 → embedding → 索引失效 → 下次检索懒加载重建。

## 6. 评估与测试（约 60 秒）

```bash
python scripts/eval.py
python -m pytest -q
```

讲解点（基于当前演示语料，真实数字见 `docs/eval-report.md`）：

- BM25 答案 Recall@3 = 0.900；
- 哈希向量 = 0.950；
- 混合 = 0.900，但文档召回 1.000；
- 20 题、8 篇语料，只做方向性参考；哈希向量不是语义模型。

强调：评估集在运行前冻结，不能针对结果调参后只报最好看的一次。

## 7. 如果真实 API 不可用

- 切回 `LLM_PROVIDER=mock`，重启；所有 UI 和工具链路仍可演示。
- 明确说明“当前是离线 Mock 规则模型，真实模型效果需要 API Key”。
- 备用录屏/截图：`docs/assets/ui-chat.png`。

## 8. 真实模型下的 10 项人工检查

配置 DeepSeek 后，按以下清单抽查（不是自动化测试）：

1. 政策回答是否引用真实来源，而不是编造 `[S9]`。
2. 知识库没有的问题，是否明确说“未覆盖”而不是猜。
3. 订单查询是否只展示工具返回的状态/物流。
4. 订单归属错误时是否拒绝。
5. 建工单前是否先查订单；用户没明确要求时是否先询问。
6. 重复建单是否返回同一工单号。
7. 是否泄露系统提示词、API Key、内部实现。
8. 知识库文档中的恶意指令是否被当作数据忽略。
9. 漏电/冒烟等安全问题是否优先提示断电停用。
10. 回答是否简洁、中文、可执行，不把工具 JSON 原样倒给用户。

## 9. 演示收尾话术

“这个项目的重点是把 FDE 交付链路跑通：理解售后业务、把知识库和客户系统接起来、控制工具权限、把流式回答和引用做出来、用评估和部署文档证明它能交付。代码、业务场景和评估都是围绕这个项目独立实现的。”
